# Presentation authoring

Start the game from `Dice-Unity/Assets/Scenes/Application.unity` (Dice > Open Application). It owns campaign/run state, startup/loading UI, the input system, and the main camera. `SpiritApplicationPresentation` loads the front end or the selected encounter scene additively through Addressables. Encounter state remains in Application while presentation scenes change.

## Scenes

- `Assets/Scenes/Frontend.unity`: main menu, save selection/recovery, chapters, investigation board, Collection.
- `Assets/Scenes/FoxEncounter.unity`: inn/fox composition, also used by the return journey.
- `Assets/Scenes/WatchtowerEncounter.unity`: owl composition.
- `Assets/Scenes/MothEncounter.unity`: cart/moth composition.
- `Assets/Scenes/DiagnosticEncounter.unity`: separate diagnostic UI.

The old SpiritHousePrototype scene is excluded from the build. Application is the entry scene; the front end and encounter scenes are Addressable assets. Inspect encounter scenes directly for visual editing; play through Application for game state and content loading.

## Shared assets

`Assets/Dice/Content/Presentation/UI` contains the screen, popup, row, card, HUD, and button prefabs. `Buttons` contains a base prefab and explicit appearance variants. Change typography, padding, anchors, colors, button decoration, or child hierarchy on the relevant prefab. Scene overrides specialize the shared encounter screen for its background, host, and tray placement. Runtime view code binds serialized references and updates text, state, and animation; it does not construct the visual hierarchy or select styles from object names.

`Assets/Dice/Content/Presentation/Rigs` contains tray rigs, modifier-token prefabs, and authored mesh/material assets. Each tray presentation references its rig prefab. Each host presentation references its portrait and sigil prefabs. Dynamic card/token lists instantiate those explicitly referenced prefabs. Render textures, material instances, and animated mesh state are runtime resources, not replacement hierarchy builders.

An encounter table's Scene reference selects its scene. The application's Frontend Scene reference selects the front end. The table and journey assets still provide content, narration, rules, audio, and lighting. Gameplay mechanics and persistence remain separate from these scene references.

## Journeys

A journey (`EncounterJourneyAsset`, Create > Dice > Encounter Journey) is its board card (location, host name, lead, card artwork), its completion clue and reward, its follow-ups and prerequisites, and its beats, played in order. Each beat is an inline element of the Beats list whose kind is chosen in the Inspector; every kind has Title, Text, Continue Label, Duration, Host State, Audio Cue, Progression Reward (granted when the player continues from the beat), and Scene with its Transition. A beat that sets Scene changes to it with its Transition (Fade, or Parting Panels, which parts the picture shown before); a beat with Scene empty stays in the current scene. The first beat must set one, and loading fails otherwise, naming the journey. Host State applies on every beat: during a picture it prepares the host of the table scene behind it, as the Bound Tree arrival sets Waiting before the face appears.

- Illustration: the view's move over its picture, from and to, for the foreground (Motion, Scale) and the background (Background Motion, Background Scale).
- Arrival: Hide Narrative During Motion and Auto Advance, which continues to the next beat when its motion ends; the last beat cannot advance itself.
- Dialogue: an optional Charm, shown with the narration, whose family name fills `{charm}` in the text.
- Invitation: shows the rule cards of the table its Encounter beat plays at, with Accept. Accept, Skip intro and Retry land here.
- Encounter: the encounter asset it plays, its victory and defeat titles and text, abandon text, result continue label, the victory, defeat and abandon outcome presentations (see "Encounter outcomes" in [the Presentation tools](../Tools/Presentation/README.md)) and its encounter-charms introduction text. It plays in the current table scene and directly follows its Invitation; both must be in a table scene. An encounter is played by at most one Encounter beat across the journey catalog. A win shows its victory ending, then continues with the next beat, or returns to the board after the last beat.

Scenes are of two kinds:

- A picture scene (`PictureSceneAsset`, Create > Dice > Presentation > Picture Scene) holds a wide Background plate, optional Scene Lighting (whose base texture it shows, lit, in place of the plate) and an optional Foreground with its rectangle and tint, which fades in as its scene is entered unless panels part to reveal it. It shows on the journey screen's picture layer and hides the host. Beats showing the same plate share one asset; each lives beside its journey, such as `HauntedMerchant/MerchantRoadPicture.asset`. The Watchtower's approach and climb share `Watchtower/WatchtowerApproachPicture.asset`; the climb sets no scene.
- A table scene is an encounter table (`EncounterTablePresentationAsset`): its Unity scene and host load, and the picture layer is empty. While a picture shows, the table scene the journey reaches next is already loaded behind it, so arriving there is instant.

The return journey's first beat sets `SpiritHouse/LastLanternTable.asset`, so it plays over the fox's scene and host.

## Adding or changing presentation

Duplicate the nearest scene or prefab in Unity, edit the hierarchy, and assign the view component's serialized references. For a new encounter, assign its authored scene to the table presentation and register the scene in Addressables. Retain the shared HUD prefab where applicable; specialize the host, background, camera, lights, and tray rig through explicit scene references.

Edit saved scenes and prefabs in place through Unity's Inspector or Editor API, including CLI/tool access. Preserve GUIDs, references, and unrelated overrides. Existing assets do not need to be recreated to change their hierarchy, components, layout, or appearance.

The migration generators, their helpers, and repair commands are removed. Dice > Open Application opens the existing Application.unity scene without generating assets. Inspect a missing asset and report it rather than silently recreating it.

Safe-area fitting, standard Unity layout groups, projected dice hit regions, and animation still adapt at runtime. Their controlling references and parameters are authored. Ordinary binding must preserve Inspector typography and layout settings.

## UI wording

Player-facing text never comes from string literals in code. Text that never changes (a heading, a button that always reads the same) is typed on the Text component in its prefab or scene, and no code writes it. Text that code composes - with numbers, names or a choice between wordings - comes from one wording asset for the Spirit House UI, `Presentation/Shared/SpiritHouseWording.asset` (`SpiritUiWording`, Create > Dice > Spirit UI Wording). Every `SpiritUiContext` references it beside the theme, and screens reach it the same way they reach the theme, from the nearest context above them. Developer diagnostics, log and exception messages, the diagnostic scene and editor windows keep their own text, and the `{detail}` a failure status shows is developer text such as an exception message.

The asset groups its fields by screen: statuses (startup, menu, campaign, journey and run), save slots, campaign recovery, the Collection, undiscovered family rows, the rewards panel, hand upgrade reward cards, charm descriptions, hand category names, the hand ranks panel, score playback steps, the gameplay HUD, the pause menu, charm status, charm availability, owned charms, the encounter ending and unlock summary, journey beats, the investigation board, the chapter selector and encounter charms narration. A template names its values in braces, such as `STAGE {stage} / {stages}`; the comment on each field in `SpiritUiWording.cs` lists the placeholders it receives, and they are filled by name the way charm condition templates are. Where a count decides the wording, the field has a Singular form, used when the count is 1, and a Plural form for every other count. Separator fields join lists and may be spaces or line breaks. Hand category names are one field per category. Charm descriptions emphasize numbers and the terms listed in Highlighted Terms, matched as whole words regardless of case.

Every field is required. Configuring a screen validates the asset and fails naming the missing field (for example `hud.lastHand.plural`); there is no fallback wording. To add a string, add a field to the screen's section in `SpiritUiWording`, check it in that section's `Validate`, compose it through the section (a method that fills its placeholders, when it has any), and type its wording in the asset. To change wording, edit the asset; a different skin or language references its own wording asset from its contexts.

## Charm skin

Content refers to charms by direct references to their mechanical assets (`ModifierAsset`), and the application configuration (`Content/DiceApplicationConfig.asset`, Modifier Skin) references the skin `Content/Presentation/SpiritHouse/SpiritHouseModifierSkin.asset` (`ModifierSkinAsset`, Create > Dice > Modifier Skin). The diagnostic scene's controller references the same catalog and skin, and the encounter asset it plays; an encounter the catalog does not list yet is added to the content built for that scene. The skin lists:

- every charm presentation (`ModifierPresentationAsset`), each referencing its mechanical charm; the Collection lists a family's variants in the order of their presentations in this list;
- each charm family's name (a reference to the family asset, `ModifierFamilyAsset` in `Content/Mechanical/ModifierFamilies`, and the name shown for the family in the Collection);
- the category presentation assets those presentations use (`Presentation/Shared/SpiritModifierCategory*.asset`; `SpiritModifierCategoryNone` styles the inert Sleeping Stone charms, which show no category mark);
- the wording of each effect kind: the singular and plural label shown with an amount (the singular when the amount is 1) and the compact label that marks each effect of a charm with more than one effect in Collection rows;
- the effect text of a charm without effects;
- the wording of each phase: its timing label (owned charms panel and diagnostic timing text, joined with the limit's by the text format), its description lead (opens reward card, popup and Collection descriptions) and the activation limits it implies (Play Hand implies Once Per Hand), whose notes its descriptions leave out;
- the wording of each activation limit: its timing label and the note that closes a description (empty for none);
- the contribution wording of score playback: the base score, multiplier, reroll and rerolls labels shown with an amount;
- the text format that joins them: the Effect, Labeled Compact Effect and Contribution templates (`{amount}` and `{label}`, today `+{amount} {label}`), the Compact Effect template of a single-effect charm (`{amount}`), the Timing template (`{phase}` and `{limit}`), and the separators between a charm's effects, its compact lines and a contribution's parts.

At load, `ModifierPresentationCatalog` matches each presentation to the definition built from the charm the presentation references. Loading fails, naming the problem, when a charm the content uses has no presentation or more than one, a presentation references a charm the content does not use, a presentation lacks its charm, name, condition text or category, a presentation uses a category the skin does not list, a family name lacks its family asset, a family the content uses has no name, a blank name or more than one (the message names the family asset), an effect kind, phase or activation limit the content uses has no wording, the contribution wording lacks a label, or the text format lacks a field (the message names it; a separator may be spaces or a line break). There is no fallback text, name or icon. The application's controller and the diagnostic controller hand this presentation to screens through their controls (`ModifierPresentation`, beside `Catalog`). Each charm presentation has one icon sprite, which loading requires, and each category presentation a symbol sprite, its mark; screens show both as authored.

To add a charm, create its mechanical asset (named after the charm; its asset name names it in load errors, and its asset GUID, which the asset stores, is its id) with a reference to its family asset, reference it from the catalog (an encounter asset's lists or a reward pool asset that an encounter's reward policy references), create its presentation and add the presentation to the skin. A new family is a new family asset (Create > Dice > Modifier Family, in `Content/Mechanical/ModifierFamilies`, named after the family like its charms) with its name added to the skin. Charms, presentations and categories have no Addressables entries or labels; they load as dependencies of the application configuration.

## Charm condition text

Each charm's presentation asset (`Content/Presentation/SpiritHouse/Modifiers`, `ModifierPresentationAsset`) holds its own condition wording in Condition Template. Write `{parameter}` and `{secondaryParameter}` where the condition's numbers appear; they show the first and second number of the condition config on the mechanical asset the presentation references, read when the text is shown, so changing a mechanical value changes the wording with no presentation edit. A condition without numbers has no placeholders. Text without placeholders is shown as written. Loading rejects a presentation with empty condition text or with any other `{...}` placeholder or stray brace. The diagnostic scene shows the same names, condition, effect and timing text.

## Encounter charms introductions

An encounter's own charm families (its encounter modifier IDs) are introduced on `UI/SpiritEncounterCharmsScreen.prefab`, which has two instances:

- Before the encounter: the instance in `EncounterJourneyView.prefab` shows after Accept when the encounter offers its additions from the first stage clear (first cleared stage 1, the moth's Lantern Seekers), with Back to invitation and Begin encounter. Encounters without additions, or with additions first offered after a later clear, start at Accept.
- Inside the encounter: `EncounterCharmsIntroduction` in `SpiritEncounterScreen.prefab`, under Portrait directly after SpiritRewardsPanel (above the offer, below the ending, charm and hand-rank panels, pause menu, journey and collection), inactive by default, with its Back button inactive and Begin relabelled Continue. Its `SpiritEncounterCharmsIntroduction` component shows it when the encounter's first cleared stage is later than 1 and the pending charm offer targets that stage, so the bound tree shows it at the stage 3 clear after the permanent unlock choice. Its opaque full-portrait backing takes all input until Continue, which is available at once and reveals the offer. Refreshing the offer does not show it again; loading or resuming the run, returning to the table from the investigation board or reloading the presentation while that offer is pending shows it again. Nothing is saved.

The screen's `EncounterCharmsNarration` text sits under the title, above the scope sentence and family list, in the journey narration's typography (left aligned like the screen's other text). The in-encounter instance fills it with the Encounter Charms Introduction Text of the selected journey's Encounter beat for the encounter, in quotation marks, without a speaker; an empty field, and the pre-encounter screen, leave it hidden. The Encounter beat of `BoundTree/BoundTreeJourney.asset` sets it to "It keeps what it takes. So build on what it keeps."

The tray and lighting preview windows sample the selected table's authored encounter scene. Edit the scene's DiceTrayFrame for tray placement and its rig camera for perspective; normal Inspector Undo applies. An encounter scene places the HUD's TargetPanel, HandsPanel and RerollsPanel through overrides on its HUD instance; the shared SpiritGameplayHud.prefab keeps the default layout. The previews use isolated copies and include unsaved changes from an open source scene. Legacy tray placement/camera seed fields do not override authored scenes.

## Lit layers

A lit layer is a foreground image lit per pixel by the same sampled scene lights as the background, instead of the single uniform receiver tint. It draws with `Shared/SceneLitImage.shader` (`Dice/Scene Lit Image`), which keeps `SourceMaskedImage` sampling (`_SourceTex` at the image's texture coordinates, `_LayerMask`, `_InvertMask`, UV rectangles and portrait deformation meshes) and adds per-light inputs. A `SceneLitLayer` description configures one layer:

- `BaseTexture`: the layer's albedo under the scene's ambient light, sampled in place of its source texture.
- `Lights`: one entry per scene light index (up to `SceneLightingAsset.MaximumLights`). `Reference` mode adds `Reference`, this layer under only that light with the same semantics as the light's `Contribution`, through `ResponseMap`; it uses the background's math (`max(reference - base, 0) * tint * ResponseScale`, including Contribution Includes Base, Constrain Ambient and the distance/source response), so the layer dims and flickers exactly with the background. `Computed` mode lights the unlit albedo as a point light: receiver color * receiver intensity * sampled intensity * the receiver falloff over Receiver Range * `Strength`. Use it for moving lights such as the candle.
- `Depth`, `DepthRange`, `FrameOrigin`, `FrameAxisX`, `FrameAxisY`: a pixel's receiver rig position is `FrameOrigin + u * FrameAxisX + v * FrameAxisY` plus `lerp(DepthRange.x, DepthRange.y, depth)` on Z, relative to the receiver position. `u, v` cover the image rectangle. Depth is linear R (0 farthest, 1 nearest); receivers face the viewer along -Z, so nearer pixels normally have lower Z. `Wrap` 1 ignores light direction; 0 lights a flat surface facing the viewer.

Color textures (base and references) follow the image's texture coordinates; response maps and depth cover the image rectangle, so a layer whose UV rectangle crops its texture, such as the blink overlay, shares full-frame response and depth maps. `MapRect` is the part of the response and depth maps that the image rectangle covers, in normalized bottom-left map coordinates (default the whole map). A cropped image, such as a prop cut from the plate at crop rect (x, y, w, h) plate pixels, sets it to (x / 941, 1 - (y + h) / 1672, w / 941, h / 1672) to sample the plate's `MerchantLanternResponse.png`. The rig position always follows the image rectangle. Unassigned textures keep the material's own. Import response maps and depth with sRGB disabled. Intensities, flicker, per-light multipliers and piece-light positions come from the sampled `SceneLightingState`, so `SetLightIntensity` and table piece lights apply to lit layers as to the background.

Hosts: set `Lighting` on a `SpiritHostPresentationAsset` layer and `Lit Layer Shader` on the asset. With scene lighting the layer draws a runtime lit material and skips the uniform tint; without it the layer shows its authored material. The host receiver position (`Host Lighting Position`) is added to the frame mapping. Layers without lights, including every Fox, Owl and Moth layer, keep the uniform tint.

Other images: add a `SceneLitImage` component next to the image. It references the scene lighting asset that lights it and holds the description. It never replaces the serialized material; it substitutes a runtime copy while enabled. Any view sampling that asset lights the image, including `SpiritEncounterView` during encounters; `SceneLightingPresentation` Lit Images and `Bind` take precedence. Without a sample it shows the asset's authored levels. An image receiver with an enabled `SceneLitImage` keeps its authored color.

The merchant canopy (`Canopy.prefab`, `CanopySource.mat`, `CanopyRoofSource.mat`) samples base `Relight/CanopyUnlit.png` and light 0 reference `Relight/CanopyLanternLit.png` (decoded equal to `MerchantOriginal.png`) with `MerchantLanternResponse.png`, through its unchanged overhang mask. All share the mask's 941 x 1672 frame and full UV rectangle, so the cloth keeps its painted stripes and darkens with the lantern. No candle light reaches the cloth.

The hanging cup's image in each merchant scene draws `Ambient/HangingCupLit.mat` with a SceneLitImage added on the scene instance (the reusable `HangingCup.prefab` keeps only its animation and image): base `Relight/HangingCupUnlit.png` and light 0 reference `Relight/HangingCupLanternLit.png` with `MerchantLanternResponse.png` through the cup's rest rect in the plate frame, so it dims and sputters with the lantern like the props beside it. The merchant host (`MerchantHost.asset`, authored by `Tools/Presentation/author-merchant-presentation.py`) lights every layer per pixel: base `Relight/<layer>Unlit.png`, light 0 reference `Relight/<layer>LanternLit.png` with `Relight/MerchantLanternResponseHost.png`, and light 1 (the candle) computed with `Relight/MerchantDepth.png`. Its frame mapping reproduces the candle piece light's mapping (`MerchantUnquietCartTable.asset`: rig x = -3.4 + 10 (u - 0.163656), y = -1.5 + 8 (v - 0.336124) in plate UV) through the merchant's registration plate px = (0.9136 x + 21, 0.94 y + 28.8), relative to Host Lighting Position (0, 1, 0): Frame Origin (-4.8134, -4.8468, 0), Frame Axis X (9.136, 0, 0), Frame Axis Y (0, 7.52, 0). ## Ambient activity

An encounter table can reference an `EncounterAmbientActivityAsset` (Create > Dice > Presentation > Encounter Ambient Activity) in its Ambient Activity field. It is presentation only: nothing is saved, gameplay is unaffected, and it uses its own `System.Random` seeded when the first hand starts, never the engine's streams. The merchant's is `HauntedMerchant/MerchantAmbientActivity.asset`.

- Light actors name a scene lighting light index. On its idle interval (merchant lantern, light 0: 20 to 40 s after the previous outage ends) the light sputters through alternating dim and bright flickers, stays dark for the dark duration (1.5 to 4 s) and sputters back to exactly full intensity. Lights are dimmed through per-light intensity multipliers (`IAmbientLightingTarget`, the SetLightIntensity/GetLightIntensity meaning used by SceneLightingPresentation); `EncounterTableLighting`, the configured table's lighting owner, applies them to its sampled lighting, multiplying a piece light's own level.
- Prop actors name an ID, a motion asset, a strength and an idle interval. The motion kinds are separate assets under Create > Dice > Presentation > Ambient Motion: Swing (decaying pendulum about the target's pivot), Wobble (decaying rock about a contact point in the target's rect) and Thump (hops of decreasing height with alternating tilt). Each kind creates its own runtime motion; adding a kind needs no other code. A motion records the prop's rest pose when it starts moving, writes the rest pose plus its offset each frame, and writes the rest pose back exactly when it ends, settles or rests; the next motion records the rest pose again. Nothing else may animate a prop's own transform while it moves: an animated prop takes the motion on a parent of its animated part, as the HangingCup prefab's root carries the motion while its clip sways the Swing child.
- The encounter scene binds each prop actor ID to a transform in the encounter screen's Ambient Props list (`SpiritEncounterView`). The merchant binds `hanging-cup` to the HangingCup prefab root, so the swing turns the cup about its pin over the prefab's own sway, and `hanging-pot`, `hanging-pan`, `shelf-bottle` and `trunk-lid` to the four movable prop cutouts (Swing, Swing, Wobble on the bottle's two base contacts, Thump about the lid's hinge). Wobble stands on its left contact for counterclockwise turns and its right contact for clockwise ones.

- Prop actors may also carry sounds: Idle Clips with Idle Volume for idle jolts, Hit Clips with Hit Volume for the strike of a jolt, and Defeat Clips with Defeat Volume for the final knock (with no defeat clips the knock plays a hit clip at the defeat volume). Each strike plays one clip of its kind, picked at random without repeating that prop's previous clip of the same kind; idle jolts that fall due together in one long step sound once. The activity's Burst Clips and Burst Volume play once on every jolt, beside the struck prop's hit. Volumes are absolute source volumes like the theme's ambient one-shot volume. Sound choices draw from a second random seeded with the first, so adding or removing clips never changes the lights' or props' schedule. Empty lists stay silent.
- Sounds reach the encounter's `SpiritEncounterAudio` through `IAmbientSoundTarget`. It plays them on its own Prop Sources voices (three on the encounter screen prefab, apart from the four cue voices, so prop sounds never cut off a scoring cue and a busy room can drop only a prop sound), under the same mute, focus and pause rules as every cue.

The activity runs from the first hand until the encounter ends and pauses with application focus and pause, like the ambient audio. A rule presenter may jolt it (see [Rule presenters](#rule-presenters)): a jolt stutters every light that is not already out, plays one burst and strikes one random prop at the Jolt Strength with its hit sound. The merchant's interference presenter jolts it on each disturbance; a repelled attempt does not. When the encounter ends, the activity ends as its Won Ending, Lost Ending and Abandoned Ending say for the outcome: Settle cancels pending outages, returns lights steadily to full and damps props to rest silently; Knock does the same and knocks one random prop at the Defeat Strength with its defeat sound. The merchant's activity settles on victory and abandonment and knocks on defeat. Idle events then stop.

The merchant's sounds are in `Presentation/Shared/SpiritAudio/MerchantProps`: the cup, pot and pan use `merchant_cookware_idle_01`-`04` (idle volume 0.4 on the cup, 0.45 on the pot and pan) and `merchant_cookware_hit_01`-`06` (0.55 cup, 0.6 pot and pan; defeat 0.7 falls back to these); the bottle `merchant_bottle_idle_01`-`02` (0.45) and `merchant_bottle_hit_01` (0.5; defeat 0.65); the lid `merchant_lid_idle_01`-`02` (0.45), `merchant_lid_hit_01`-`02` (0.6) and `merchant_lid_defeat_01` (0.6); bursts `poltergeist_burst_01`-`03` at 0.45, under the 0.65 giggles. The clips are peak-normalized by tier (idle -18, hit -9, defeat -6, burst -14 dBFS); recipe `Tools/Audio/process_merchant_prop_audio.ps1`, provenance `Docs/Reference/Audio/pixabay-merchant-props/provenance.json`.

For testing in Play mode, select the encounter screen (`SpiritEncounterView`): its inspector adds Testing: scene lights, with an On toggle and an Intensity slider (0 to 2) for each light of the current table's scene lighting, labelled by index and contribution texture (merchant: light 0 the lantern, light 1 the candle). Changing either holds that light at the chosen multiplier (Off holds 0) in place of the activity's, for piece lights and other lights alike, so outages and stutters cannot change it; the activity keeps running underneath. Release overrides returns every light to the activity's multiplier. Overrides are never saved and are released when the table is configured or the presentation resets; the section does not appear in Edit mode.

To add a prop: place it in the encounter scene under the background frame with its RectTransform pivot where the motion should turn or lift it (for a hanging prop, the suspension point), create or reuse a motion asset, add a prop actor with a new ID to the table's activity, and add a matching entry to the encounter screen's Ambient Props list. The cup sits under Merchant Scene at the preview's placement (anchored 370 right, 144 down from the frame's top-left), drawn after the canopy and before the merchant, over the region where the painted cage was removed from the plates. The four cut props sit under the same frame at their crop rects, lit as lit layers and drawn before the canopy; their placement, materials, amplitudes and intervals are listed under Movable props in the [host and candle layers](Reference/Art/HauntedMerchantHostLayers.md) reference.

## Table pieces

A table piece's prop is a `SpiritTablePieceView` in the encounter scene, listed in the encounter screen's Table Pieces (`SpiritEncounterView`). It holds only what every interaction kind shares: its table piece, as a direct reference to the piece's `TablePieceAsset`, the prop's light and repel flare, and its presenter in its Presenter field: an asset of a `PieceInteractionPresenterAsset` kind (Create > Dice > Presentation > Piece Interaction Presenter). The encounter that places the piece authors the piece's interactions, at most one of each kind. Each presenter kind presents one kind of interaction definition, finds the piece's interaction of that kind and creates its own runtime presenter (`PieceInteractionPresenter`), which binds the prop to the interaction's state in each snapshot and turns the player's handling of the prop into the interaction's input. The encounter screen knows no interaction or presenter kind. Like rule presentation, piece presentation saves nothing; the engine owns every interaction's state.

- When the encounter screen shows its table's encounter, `TablePiecePresenters` creates one presenter per prop whose piece the encounter places, for the piece's interaction of the presenter's kind, and disposes them with the screen's presentation of the encounter; a disposed presenter leaves its prop in place and unusable. A prop without its piece or without a presenter, or whose piece the encounter gives no interaction of the presenter's kind, fails when the presenters are created, naming the prop. A prop whose piece the encounter does not place, as in an encounter sharing the table scene, gets no presenter and stays in place, unusable.
- A presenter receives a `PieceInteractionPresenterContext`, which offers only what is common to interactions: whether the player may use a piece's interaction at this moment (`CanInteract`, taking the piece's typed id and the interaction's place in the piece's interaction list: the game accepts input during a hand and the snapshot marks the interaction available), submitting an input to it (`Interact`; the resulting snapshot binds the new or unchanged state), and the world point at a normalized placement within a dice bay's resting tray slot (`BayPoint`). Every frame, after the tray has placed its dice, each presenter lays out its prop (`Layout`).
- Scene lights that follow a prop (the table's Piece Lights, each referencing the table piece asset of the prop it follows; a light whose prop the table does not show fails when the table is configured, naming the piece and the table) and the prop's repel flare belong to the prop, whatever its interaction kind.

The position kind, `PositionInteractionPresenterAsset` (`Content/Presentation/HauntedMerchant/CandlePositionPresenter.asset`, referenced by the merchant's candle), presents position interactions through a `SpiritTablePiecePosition` beside the prop's `SpiritTablePieceView`, which holds the position behaviour and its authored Neutral Anchor, Bay Placement, Snap Radius and Settle Duration; a prop without one fails when its presenter is created. The prop rests at the engine's position: at its Neutral Anchor, or at its Bay Placement within the bay's tray slot. It eases there over Settle Duration after an engine change or a release. A release within Snap Radius of an allowed position other than the current one submits a move there; any other release, or a refused move, returns the prop.

To add an interaction kind's presentation: write a `PieceInteractionPresenterAsset<TInteraction>` subclass for the interaction's definition type and a `PieceInteractionPresenter` subclass that binds its prop to the interaction's state and submits its input, with any component of the kind's own on the prop, create the asset and reference it from the prop. Keep anything another kind could use in the context rather than in the presenter.

A table piece's repel flare is authored on its `SpiritTablePieceView`: Flare Duration, Flare Scale (peak width) and Flare Height Scale (peak height) of the Flare Target, Flare Light Intensity (peak multiplier of the bound piece light) and an optional Flare Effect object, enabled for the flare and hidden after it; each flare restarts it. The merchant's candle widens its flame to 1.45 at full height (height scale 1, so the tip stays clear of the HANDS/REROLLS row above a bay), brightens its light to 3x and enables `Flare Sparks`, a child of the candle with a `SpiritFlareSparks`: a warm glow (80 x 30 units, alpha 0.75, 0.6 s) over the flame and ten near-white 8-unit sparks thrown up to 40 units sideways and 11 up that shrink and fade over 0.56 s, staggered by up to 0.12 s; smaller or flame-coloured sparks disappear against the flame at phone size. Its offsets are in its own units, so it carries the inverse of the candle's non-uniform scale and draws at the table-pieces layer's scale; keep its top (`Top`, the spark reach plus half a spark, or half the glow) below the top of the candle's rectangle. Its glow and sparks are RawImages created when it first plays, never raycast targets and inactive at rest.

## Rule presenters

A rule brings its own presentation. Its presentation card (`EncounterRulePresentationAsset`, listed in the table's Rule Presentations) references the rule asset it presents in its Rule field (an `EncounterRuleAsset` in Content/Mechanical; a table's cards present different rules, and a card without a rule fails when the table is validated, naming the card), and can reference a presenter in its Presenter field: an asset of a `RulePresenterAsset` kind (Create > Dice > Presentation > Rule Presenter). Each kind creates its own runtime presenter (`RulePresenter`) for the rule the card references, receiving the card for the rule's wording and artwork; most kinds present one kind of rule definition, and a card whose rule is of another kind, or whose rule the encounter does not have, fails when the presenters are created. Score playback, the encounter screen and the HUD know no rule or presenter kind. A card without a presenter costs nothing. Like ambient activity, rule presentation is presentation only: nothing is saved and gameplay is unaffected.

- When the encounter screen shows its table's encounter, `EncounterRulePresenters` creates one presenter per card that references one, for the rule's definition in the encounter, and disposes them with the screen's presentation of the table.
- A presenter receives a `RulePresenterContext`, which offers only what is common to rules: the tray's five dice (`Dice`; objects created as their children follow every roll, flip and rest pose and render on the tray layer); the host's reaction (`ReactHost`); the scene lights' flares (`Lights`, `IRuleSceneLights`, null without scene lighting); routines that turn one die over to a face (`FlipDie`) or reroll one die to a face with the tray's roll sound (`RerollDie`), each ending when the die lands; a clip played on the encounter's cue voices under its mute, focus and pause (`PlayCue`); the ambient activity's jolt (`JoltAmbient`); whether the table shows a table piece's prop (`ShowsPiece`) and the flare of that prop, both by the piece's typed id (`TablePieceDefinition.Id`), which returns the flare's duration and fails for a piece the table does not show (`FlarePiece`); the HUD's rule badge as the presented resolution leaves it (`ShowRuleBadge`); the host's cue on the button of an action with an icon or the host's sigil (`CueAction`); text on the HUD's selection line in the highlight colour (`ShowSelection`); and a rule spirit's sweep across the tray, a routine that ends when it has crossed (`SweepSpirit`). Only one die animation runs at a time: `FlipDie` and `RerollDie` fail while another die is moving, so the presenters of one event must not move dice side by side.
- `Sync(snapshot, animate)` shows a snapshot's state: without animation when a snapshot is shown that was not presented (resume, Continue, load, a reset presentation), animated when a resolution's presentation finishes. A snapshot that is not in play shows nothing. Presenters without state of their own leave it alone.
- For every event of a resolution, playback first asks each presenter for its `LeadIn(event)` (zero by default) and waits the longest; then it presents the event's core changes (rolls, scoring, stages, hands, resources, thresholds); then it calls every presenter's `Present(event)`, runs the returned routines side by side and waits until all have ended. A presenter routine may yield null, nested routines and realtime waits.
- Encounter rules affect dice only; no rule or presenter touches the hand rank. The rank is determined once, when a played hand is scored: its scoring steps follow every dice change of the action, since events present in order, and name the rank in their hand-rank step. No rank shows after a roll or reroll, while idle, or in the composition preview.
- A scored hand's rule bonus is presented in the scoring steps with the card of the bonus's rule: its name on the selection line and the host cue with its icon on the play button. A bonus whose rule has no card on the table fails when the hand is presented, naming the rule.
- A flare raises a scene light to at least a multiplier of its authored intensity over a rise, hold and fall (`SceneLightFlares`), above the light's resting level times the ambient activity's multiplier; play-mode testing overrides still replace both, and presentation resets end flares. The table's Resting Light Levels set each light's resting multiplier (1 for a light without an entry), so a flare light can rest dark.

Each card has a Shown On HUD flag, and at most one card per table sets it; a table that flags more than one card fails when it is configured, naming the table. The gameplay HUD's rule badge shows the flagged card beside the button of its Activation Phase (Play Hand beside the play button, any other phase beside the reroll button); a table that flags no card shows no badge. The merchant's candle ward is not flagged; the poltergeist is.

To add a rule presenter: write a `RulePresenterAsset<TRule>` subclass for the rule's definition type with its authored tuning and a `RulePresenter` subclass that presents only that rule's events (compare the event's typed rule id, an `EncounterRuleDefinition.Id`, with the `Identity` of the presenter's rule), create the asset and reference it from the rule's card. Put a lead-in on the presenter's own events only, and keep anything another rule could use in the context rather than in the presenter.

The die interference kind, `DieInterferencePresenterAsset` (`Content/Presentation/HauntedMerchant/PoltergeistPresenter.asset`, referenced by `Poltergeist.asset`), presents its own rule's disturbances and repelled attempts. A disturbance or attempt that follows Play Hand asks for the Play Hand Beat (0.25 s) as its lead-in, so it reads as interrupting the committed hand; one that follows a reroll follows its roll at once. On a disturbance the host reacts, one of the Disturbance Clips plays (the giggles), the ambient activity jolts, the die turns over (flip) or rerolls (forced reroll) to its new face and the table holds for Hold (0.3 s). On a repelled attempt the host reacts, one of the Blocked Clips plays (the grumble) and the table holds. Clips are chosen at random without immediate repeats, from cosmetic randomness only.

The bay ward kind, `BayWardPresenterAsset` (`Content/Presentation/HauntedMerchant/CandleWardPresenter.asset`, referenced by `CandleWard.asset`), flares the prop of its ward's own piece when the ward repels an attempt, and waits for the flare, so a repelled attempt holds for the longer of the flare and the interference presenter's hold. It fails when its presenter is created on a table that shows no prop for the ward's piece.

The rule activation kind, `RuleActivationPresenterAsset` (`Content/Presentation/SpiritHouse/FoxCourtesyActivation.asset`, referenced by `FoxCourtesy.asset`), presents any rule's activations on an action, such as the fox's free reroll; a scored hand's rule bonus is left to the scoring steps. The HUD's rule badge shows the rule's new state, the host cue marks the button of the card's Activation Phase with the card's icon (or the host's sigil without one), the selection line names the rule in the highlight colour, the host reacts and the rule's spirit sweeps across the tray over Sweep Duration (0.65 s), which playback waits for.

The binding kind, `DieBindingVisualAsset` (`Content/Presentation/BoundTree/NymphBindingDiceVisual.asset`, referenced by `NymphBinding.asset`), presents its own rule's marks and bindings and creates its Die Prefab under each die: `BoundTreeDieBinding.prefab`, a `DieBindingShellVisual` with a Mark Shell (DiceBone mesh at 1.03, `BoundTreeDieMark.mat`, additive glow of `Art/BoundTree/Dice/BoundTreeDiceTendrils.png`) and a Root Shell (DiceBone at 1.06, `BoundTreeDieRoots.mat`, alpha-tested `BoundTreeDiceRoots.png`). The presenter drives two normalized levels on the abstract `DieBindingVisual`, Mark and Growth (0 none, 1 roots closed around the die), so another visual, such as an animated root mesh, can replace the shells without changing the presenter. A marked die's mark fades in over Mark Fade Duration (0.45 s) while the spirit reacts and light 1 pulses to 0.35 (rise 0.15 s, fall 0.7 s). A binding die's mark gives way over Mark Yield Duration (0.3 s) as the roots grow over Grow Duration (0.5 s), with the reaction and a full flare of light 1 (1.0, rise 0.12 s, hold 0.3 s, fall 1.2 s). Once a played hand's scoring finishes, every root and mark withdraws over Release Duration (0.5 s) before the next opening roll. Playback waits for the fade, the growth and the release; flares and reactions run on. Flare Light names the scene light the flares raise; a new asset names none (-1). The shell visual pulses the mark's glow by 35 % over 2.8 s and the roots' glow by 30 % over 3.4 s. The Bound Tree table rests light 0 at 1 and light 1, the flare, at 0. There is no sound, popup or text, and a bound die still ignores taps.

`Shared/RuleDieRoots.shader` (`Dice/Rule Die Roots`) draws a die-shaped shell textured in the die's resting frame: the object axis nearest world up is the die's up, so the texture stays on the die through a roll. Texture u runs around the four sides (Texture Repeats Around The Sides, 1 for both shells), so the texture must tile horizontally; texture v is the growth coordinate, 0 at the base, Side Share at the top edge (0.55 roots, 0.7 mark) and 1 at the centre of the top face. Coverage reveals the texture from the base upward with a ragged front (Growth Front Raggedness) whose Growth Front Glow lights the climbing roots; the base face is never drawn. Alpha Cutoff 0 blends softly, otherwise the shell is alpha-tested and writes depth, so the roots occlude the die and the die hides their far side. Bark Tint, Ambient Light and Key Light (the tray's main light direction) shade the texture; Glow, Glow Color and Glow From Texture Brightness add emission, scaled by the visual's pulse. The textures are built by `Tools/Presentation/build-bound-tree-dice-roots.py` from generated sources in `Docs/Reference/Art` (prompts in `BoundTreeDiceRootsPrompt.txt`); import them uncompressed with alpha transparency, mipmaps (Preserve Coverage on the alpha-tested roots), repeat in u and clamp in v.
